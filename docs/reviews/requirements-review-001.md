## 1. エグゼクティブサマリー

原始要件は、ドメインモデル（1顧客＝1口座）、顧客・口座メンテナンス、入金・出金・振込、取引履歴照会、排他制御と入力検証を、コンパクトかつ比較的明確に記述しています。銀行勘定系のエッセンス（残高≧0、振込のアトミック性、行ロック）は原始要件として言及されています。

一方で、**実装開始を妨げる未決事項が複数存在**します。

- **明確な不整合**: Accountの属性一覧に「ステータス」が存在しない一方、解約処理は「口座のステータスを解約済みに変更」すると記述しています（§1 vs §2.1）。
- **状態遷移の未定義**: 解約済みの顧客・口座に対してどの操作（入金・出金・振込・情報更新・履歴照会）が許可されるかが未定義です。
- **金額境界の欠落**: 入金は1円〜10,000,000円と明確ですが、出金の上限、振込の下限・上限は未定義です。
- **同時実行・二重処理**: 行ロックは明記されていますが、冪等性、ロック順序、デッドロック・タイムアウト・リトライの扱いが未定義です。
- **インターフェース層の未定義**: 操作者・認証・認可・インターフェース形式・エラー契約・金額のデータ型・日時・タイムゾーンが未定義です。

**Requirements Readyゲート判定: `FAIL`**（判定根拠は §19 参照）。

## 4. 主要な結論

1. **要件はコンパクトで、核心的な不変条件（残高≧0、振込アトミック性）の意図は読み取れる**が、銀行システムを実装するには**決定が必要な事項が多数**残る。
2. **Account状態属性の不整合**（§1 モデル表 vs §2.1 解約処理）は明確な不整合であり、スキーマ設計と状態遷移定義に直結する。
3. **解約済み顧客・口座への操作許可**が未定義であり、全機能の状態遷移とエラー契約に波及する最重要の未決事項。
4. **金額境界**は、入金のみ完全に定義されており、出金の上限・振込の下限/上限が未定義。
5. **同時実行・二重処理**は行ロックの言及のみで、冪等性・ロック順序・デッドロック対策が未定義。
6. **インターフェース層（操作者・認証・認可・API/UI・エラー契約・金額型・日時）**がほぼ未定義。
7. Requirements Readyゲートは **`FAIL`**。Issue #1の成果物としては完結するが、charter基準の「実装を妨げる未決事項の決定」はKooの決定待ち。

## 5. 矛盾・不整合

### CON-001: Accountに状態属性が存在しない一方、解約処理が口座ステータスを変更する【明確な不整合】

- **事実（原始要件）**: §1 ドメインモデルのAccount属性は「口座番号、顧客ID（FK）、残高、作成日時」のみで**ステータスを含まない**。一方 §2.1「顧客削除（解約）」は「該当顧客**および口座のステータス**を『解約済み』に変更」と記述する。
- **指摘**: Accountに状態属性が定義されていないため、「口座のステータスを解約済みに変更」を実現するための属性がモデル上存在しない。
- **推奨案**: Accountに状態属性（例: 有効/解約済）を追加し、Customerのステータスと口座の状態の対応関係を仕様で固定する。実現方式（ステータスカラム vs deleted_at）はADR候補（ADR-CANDIDATE-006）。
- **未決事項**: DEC-001〜004（解約後の操作許可）と合わせてKooが決定する。

### CON-002: 入力契約の非統一（「顧客IDまたは口座番号」と「顧客IDのみ」）【矛盾ではなく検討事項】

- **事実（原始要件）**: 入金・出金は「顧客ID（または口座番号）」、振込は「出金元顧客ID、振込先顧客ID」、履歴照会は「顧客ID」。
- **指摘**: 操作ごとの入力契約が非統一である。これは原始要件の**内部矛盾ではなく、統一要否を検討すべき仕様確認事項**として扱う（Agent Bレビュー m-2 反映）。1顧客＝1口座のため顧客IDで口座を一意特定できるが、入力契約をどちらに固定するかの決定が必要。
- **推奨案**: 入力契約を「顧客IDのみ」または「顧客IDと口座番号の両対応」のどちらかに統一し、顧客IDと口座番号の対応不一致時のエラー扱いを定義する（DEC-007, DEC-008）。

### CON-003: 解約エラー制約の「マイナスの場合」の意味

- **事実（原始要件）**: §2.1「残高が 0円 でない場合は削除不可（1円以上残高がある、**またはマイナスの場合**はエラー）」。
- **解釈**: 残高は常に0円以上と導出されるため（§2.2 出金後残高マイナス不可）、正常系では残高マイナスは発生しない。この記述は、異常・データ不整合時の防御的制約と読むのが自然。
- **指摘**: 「残高≧0」が不変条件として保証されるなら、「マイナスの場合」は到達不能な分岐であり、記述が冗長または不変条件の明示的定義を欠くことの表れ。
- **推奨案**: 仕様書で「残高は常に0円以上」を不変条件として明文化し、解約条件は「残高が0円のときのみ可能」と整理する（REQ-DOM-005と関連）。

### CON-004: Requirements Ready通過には後続の意思決定工程が必要（プロセス注記）

- **事実（正本）**: `simulation-charter.md` §6 Requirements Ready は「**実装を妨げる未決事項が決定されている**」ことを要求する。一方 Issue #1 のScope（対象外）は「未決事項の独断による確定」を禁止し、本Issueは要件レビュー（分析・整理）までの範囲。
- **指摘**: これは**正本間の矛盾ではなく、正常なフェーズ分割**である。Issue #1が分析を担当し、別の意思決定工程（KooによるBlocker決定）を経てRequirements Readyを通過する構造は成立する（Agent Bレビュー m-2 反映）。
- **推奨案**: Requirements Readyゲートは、要件レビュー成果物の検収とKooによる未決事項の決定を分離して運用する。本報告書では §19 のとおり両者を分離して報告する。

## 8. 状態遷移上の未定義事項

1. **顧客の状態遷移**: 「有効 → 解約済」のみが §2.1 から導ける。再有効化（解約取消）は未定義（GAP-024）。
2. **口座の状態遷移**: 口座に状態属性がないため、解約時に口座がどう変化するか未定義（GAP-001）。
3. **解約済み状態で許可される操作**（最重要）:
   - 解約済み口座への入金（GAP-023）
   - 解約済み口座からの出金
   - 解約済み口座を振込先にする（§2.3 で「解約済みはエラー」と明記済み）✓
   - 解約済み口座を出金元にする（§2.3 では出金元の解約済みチェックは明記なし）
   - 解約済み顧客の情報更新（GAP-002, DEC-003）
   - 解約後の履歴照会（GAP-003, DEC-004）
4. **振込の状態条件**: 振込先が存在しない/解約済みはエラーと定義済み（REQ-TRF-003）。出金元の解約済みチェックは未定義（GAP-002, GAP-023）。
5. **全額出金の状態条件**: 残高0円の口座に対する全額出金は「出金金額0円」となり、「出金金額が0円以下の場合は不可」（§2.2）と衝突し得る（§9 境界値の不足を参照）。

## 9. 正常系・異常系・境界値の不足

### 境界値: 入金（定義済み）

- **事実（原始要件）**: §2.2「1回あたり 1円以上 ～ 最大 10,000,000円（1,000万円）まで」。
- **指摘**: 境界の包含関係は曖昧ではない。以下のとおり**Defined**として登録する（要件台帳 REQ-DEP-001）。
  - 0円: **不可**
  - 1円: **可**
  - 10,000,000円: **可**（「まで」は包括的と読む）
  - 10,000,001円: **不可**
- **注記**: この包含解釈（上限値を含む）は「最大〜まで」の自然な読み。仕様書で明文化することを推奨（Kooが包含関係を変える場合のみ再定義）。

### 境界値: 出金（上限未定義）

- **事実（原始要件）**: §2.2「出金後の残高がマイナスになる場合は処理不可」「出金金額が 0円 以下の場合は不可」。
- **指摘**: 下限側（0円以下不可）は定義済みだが、**上限が未定義**（GAP-004）。残高上限がないため、理論上は残高まで出金可能。全額出金との関係も含め上限の要否を決定する必要がある（DEC-005）。

### 境界値: 振込（下限・上限未定義）

- **事実（原始要件）**: §2.3 に金額範囲の記述なし。
- **指摘**: 下限・上限ともに未定義（GAP-005）。入金の上限（10,000,000円）と整合させるか独立に定めるかの決定が必要（DEC-006）。

### 正常系・異常系の不足

- 存在しない顧客ID・口座番号を指定した場合のエラー定義（入金・出金・履歴照会・振込出金元）が未定義。
- 顧客IDと口座番号の対応が不一致の場合の扱いが未定義（CON-002）。
- 履歴照会で該当取引が0件の場合の出力（空リストの形式）が未定義。
- 全額出金のエッジケース: 残高0円の口座への全額出金は「0円の出金」となり、出金金額0円以下不可と衝突する（§8-5）。「全額出金は残高が0円の場合も可（0円出金）とする」か「不可（対象外）とする」かを仕様で決定する必要がある（DEC-010 と関連）。

## 10. データ整合性とトランザクション上のリスク

| リスク | 内容 | 根拠 |
| :--- | :--- | :--- |
| R-01 振込の部分更新 | 引落・加算・双方の履歴記録が分割して適用されることで、片側だけ更新・片側だけ履歴が残る | §2.3（REQ-TRF-004: アトミック性は明記済み。実現方式はADR候補 ADR-CANDIDATE-002） |
| R-02 取引後残高の記録 | Transaction属性に「取引後残高」があるが、並行実行時に正しい残高を記録するには行ロックが前提。ロックなし経路がある場合に不整合リスク | §1, §3 |
| R-03 振込履歴のペアリング | 送金側・受取側の履歴を結ぶ識別子（振込ID等）が未定義。対当口座番号のみでは、同一時刻・同一金額の複数振込を区別できない | §1（GAP-008） |
| R-04 残高≧0の保証 | 残高が0円以上という不変条件を、入金・出金・振込・解約の全経路で成立させる必要がある | §2.2 から導出（REQ-DOM-005） |
| R-05 初期残高と履歴 | 口座開設時（初期残高0円）に履歴を残すか、残さないかの扱いが未定義 | §2.1 |
| R-06 顧客登録と口座開設の分割成功 | 顧客レコード作成成功後に口座作成が失敗した場合のロールバック要件が未定義。1顧客＝1口座の不変条件（REQ-DOM-001）に直結 | §2.1（GAP-032） |
| R-07 残高更新と履歴作成の部分成功 | 入金・出金の残高更新と履歴作成が分割適用されると、残高と履歴が不一致になる。出金の履歴作成要否も未定義 | §2.2（GAP-033, GAP-034, GAP-035） |

## 11. 排他制御・同時実行・二重処理上のリスク

| リスク | 内容 | 根拠 |
| :--- | :--- | :--- |
| R-08 行ロック＝二重送信防止の誤解 | §3 の行ロック（`SELECT FOR UPDATE` 等）は**並行性制御**であり、同一リクエストの**二重送信・リトライの重複実行**は防げない。冪等性要件が別途必要 | §3（GAP-029） |
| R-09 ロック順序の未定義 | 振込は2口座（出金元・振込先）をロックするため、並行振込のロック順序が逆だとデッドロックし得る。順序（例: 口座番号昇順）の決定が必要 | §2.3, §3（GAP-031, ADR-CANDIDATE-004） |
| R-10 タイムアウト・リトライの未定義 | ロック待ちのタイムアウト、取得失敗時のリトライ、上限回数が未定義 | §3（GAP-030） |
| R-11 全額出金の並行時非決定性 | 「全額」をいつ確定するか（処理開始時点 vs ロック取得時点）で結果が変わる | §2.2（AMB-002） |
| R-12 入金の排他制御の範囲 | §3 は「出金・振込」のみ言及し、入金の並行処理がロック対象か未定義 | §3（GAP-028） |
| R-13 履歴の不変性と順序 | 履歴の更新・削除禁止（不変性）と、同一時刻の決定的順序が未定義。ページングも未定義 | §2.4（GAP-009〜011） |

## 12. 認証・認可・操作者・インターフェース上の未決事項

- **操作者**: 誰が顧客登録・情報更新・解約・入金・出金・振込・履歴照会を実行するのか未定義（GAP-012）。実在の利用者を想定しない内部デモのため、操作者モデル（例: システム管理者のみ、バッチ処理、CLI）の決定が必要。
- **認証・認可**: 未定義（GAP-012）。内部デモの境界（simulation-charter §3: localhost/閉域）に応じた水準の決定が必要。
- **インターフェース形式**: REST API / Web UI / CLI のいずれか未定義（GAP-013）。
- **エラー契約**: エラーコード・メッセージ・HTTPステータス等の契約が未定義（GAP-014）。
- **金額のデータ型・通貨**: 円のみか、整数/小数の扱い、保存型（ADR-CANDIDATE-001）が未定義（GAP-015）。
- **日時・タイムゾーン**: 表示時刻・保存方式・監査時刻の扱いが未定義（GAP-016, ADR-CANDIDATE-010）。

## 13. 内部デモリリースに必要な運用要件

- simulation-charter §3 は「localhostまたは閉域検証環境」「実在する顧客・口座・送金・金融機関に接続しない」等の境界を定義していますが、**運用手順そのものは未定義**です。
- **不足**: health check、ログ、バックアップ、復旧手順（GAP-027）。
- **扱い**: これらは原始要件に存在しないため、要件台帳では `GAP-027` / `DEC-022` として記録し、`REQ-OPS-xxx` として既存要件と同列には登録しません（Koo決定事項）。

## 15. 未決事項ごとの選択肢、利点、欠点、推奨案

> 推奨案は提案であり、Kooの承認前は決定として扱いません。
>
> 注記: 各DECの選択肢比較は、実装開始を妨げる**Blocking項目（DEC-001〜007, DEC-012〜014, DEC-023〜025）を先に、後工程で決定可能なDeferrable項目（DEC-008〜011, DEC-015〜022）を後ろに**配置している。全DECの一覧（Blocking/Deferrable分類含む）は §14 を参照。

### DEC-001: 解約済み口座への入金可否

| 選択肢 | 利点 | 欠点 |
| :--- | :--- | :--- |
| A. 拒否（解約済み口座への入金はエラー） | 状態遷移が単純。解約後の残高変動を防ぎ、監査が容易 | 入金ミスの救済ができない |
| B. 許可 | 誤入金の救済が可能 | 解約済み口座の残高が変動し、解約条件（残高0）と矛盾し得る |

**推奨案**: A（拒否）。解約済み口座は入金元・入金先の両方で拒否し、解約後は残高が変動しない設計を推奨。振込先の解約済み拒否（REQ-TRF-003）と整合する。

### DEC-002: 解約済み口座からの出金可否

| 選択肢 | 利点 | 欠点 |
| :--- | :--- | :--- |
| A. 拒否 | 解約後は口座を凍結する意味論が単純 | 残高が0円でない状態で解約できないため、通常は出金不要 |
| B. 許可（解約時に限り残高0への精算を許可） | 解約手続きの柔軟性 | 「解約後に操作可能」という例外が増える |

**推奨案**: A（拒否）。§2.1 の解約条件「残高0円のみ」と組み合わせれば、解約時点で残高は0円であり、解約後の出金は不要。

### DEC-003: 解約済み顧客の情報更新可否

| 選択肢 | 利点 | 欠点 |
| :--- | :--- | :--- |
| A. 拒否 | 解約後は不変とし、監査が容易 | 氏名・連絡先の訂正ができない |
| B. 許可 | 誤登録の訂正が可能 | 解約済みデータを書き換える意味論が必要 |

**推奨案**: A（拒否）。解約後は参照専用とし、訂正が必要な場合は新規登録で対応する運用を推奨。

### DEC-004: 解約後の履歴照会可否

| 選択肢 | 利点 | 欠点 |
| :--- | :--- | :--- |
| A. 許可（参照のみ） | 監査・問い合わせに有用。履歴は不変なので矛盾しない | 特になし |
| B. 拒否 | データ露出を抑える | 監査目的で不可解な制約になり得る |

**推奨案**: A（許可・参照のみ）。履歴の参照はデータ整合性を壊さず、監査価値が高い。

### DEC-005: 出金の金額上限

| 選択肢 | 利点 | 欠点 |
| :--- | :--- | :--- |
| A. 上限なし（残高の範囲内） | シンプル。全額出金と整合 | 大量出金のリスク（内部デモでは低影響） |
| B. 入金と同じ10,000,000円 | 金額ルールの統一で理解が容易 | 残高が上限を超える場合は出金不能になり得る |
| C. 別途上限を定義 | 業務的に制御可能 | 追加の決定・仕様化コスト |

**推奨案**: A（上限なし・残高範囲内）を推奨。内部デモ目的では残高制約で十分。ただしKooが業務ルールとして上限を設ける場合はB/Cで決定。

### DEC-006: 振込の金額下限・上限

| 選択肢 | 利点 | 欠点 |
| :--- | :--- | :--- |
| A. 入金と同一ルール（1円〜10,000,000円） | 金額ルールの統一 | 特になし |
| B. 別ルール | 業務上の柔軟性 | 追加の決定・仕様化コスト |

**推奨案**: A（入金と同一ルール）を推奨。まずは入金の境界（1円以上・10,000,000円以下）を共通適用し、Kooが必要なら個別値を決定。

### DEC-007: 振込入力に口座番号を許可するか

| 選択肢 | 利点 | 欠点 |
| :--- | :--- | :--- |
| A. 顧客IDのみ（現状のまま） | 原始要件の記述と一致 | 入金・出金と契約が不統一（CON-002） |
| B. 顧客IDと口座番号の両対応 | 入力契約の統一 | 口座番号の参照解決・不一致エラー定義が必要 |

**推奨案**: 入力契約を統一する方向（B）を推奨するが、1顧客＝1口座の単純性から「顧客IDのみで統一」も妥当。Kooがどちらかに決定。

### DEC-012: 操作者と権限モデル

| 選択肢 | 利点 | 欠点 |
| :--- | :--- | :--- |
| A. 認証なし（単一オペレータ前提、内部デモ向け） | 実装が最小。デモに十分 | 操作者の区別・監査ができない |
| B. 単一の管理者ロールのみ | 最小限の権限境界 | ロール設計が不要でも実装は増える |
| C. 複数ロール（管理者・窓口・閲覧等） | 本格的 | 内部デモには過剰 |

**推奨案**: 内部デモの目的（simulation-charter §3）からAまたはBを推奨。Kooが決定。

### DEC-013: エラー契約

| 選択肢 | 利点 | 欠点 |
| :--- | :--- | :--- |
| A. HTTPステータス＋コード＋メッセージ | 機械処理しやすい | 契約の仕様化コスト |
| B. ステータスのみ | 簡素 | 原因特定が困難 |

**推奨案**: A（REST API前提の場合）。インターフェース形式（DEC-014）とセットで決定。

### DEC-014: インターフェース形式

| 選択肢 | 利点 | 欠点 |
| :--- | :--- | :--- |
| A. REST API | 自動テスト・CLI・UIの共通基盤として標準的 | API設計の仕様化が必要 |
| B. Web UI | デモとして視覚的 | 自動テストが増える |
| C. CLI | 最小実装 | デモの訴求力が弱い |

**推奨案**: A（REST API）を推奨。内部デモ・自動テスト・追跡可能性（charter §4）の観点で最も適合しやすい。Kooが決定。

### DEC-008: 履歴照会の入力に口座番号を許可するか

| 選択肢 | 利点 | 欠点 |
| :--- | :--- | :--- |
| A. 顧客IDのみ | 原始要件の記述（§2.4）と一致。実装が最小 | 入金・出金の入力契約と非統一 |
| B. 口座番号も許可 | 入金・出金の契約と統一できる | 口座番号の参照解決が必要 |

**推奨案**: DEC-007（振込入力）の決定に合わせて統一する。1顧客＝1口座のため、顧客IDのみ（A）でも業務上は成立する。Kooが決定。

### DEC-009: 履歴の相手情報の表示契約

| 選択肢 | 利点 | 欠点 |
| :--- | :--- | :--- |
| A. 顧客ID | 一意で識別が確実 | 人にわかりにくい |
| B. 氏名 | 人にわかりやすい | 同名の顧客と区別できない |
| C. 両方（顧客ID＋氏名） | 識別と可読性を両立 | 表示幅が広がる |

**推奨案**: C（両方）を推奨。相手情報の識別と可読性を両立できる。

### DEC-010: 全額出金の取引種別と残高0円時の扱い

| 選択肢 | 利点 | 欠点 |
| :--- | :--- | :--- |
| A. 「出金」に含める | 取引種別が単純 | 全額出金を履歴上区別できない |
| B. 別種別「全額出金」を追加 | 履歴上の識別が明確 | 取引種別の列挙が増える |
| C. 残高0円時の全額出金は拒否 | 0円出金の境界衝突を回避 | 残高0口座で全額出金APIが使えない |

**推奨案**: 種別はB（別種別）またはA（出金に含め、金額で識別）を推奨。残高0円時の扱い（C）は、「0円の出金」として許可するか「対象外」とするかを仕様で固定する。

### DEC-011: 取引種別の列挙の確定

| 選択肢 | 利点 | 欠点 |
| :--- | :--- | :--- |
| A. 原始要件どおり4種（入金/出金/振込送金/振込受取） | 原始要件と一致 | 全額出金・振込の境界種別が曖昧なまま |
| B. 5種以上に拡張 | 履歴の識別性が高い | 原始要件の4種から拡張する判断が必要 |

**推奨案**: 基本は原始要件の4種（A）とし、DEC-010の決定結果（全額出金の別種別化）を反映して確定する。

### DEC-015: ページング仕様

| 選択肢 | 利点 | 欠点 |
| :--- | :--- | :--- |
| A. 全件返却（ページングなし） | 実装が最小。内部デモでは十分 | 履歴が増えると応答が肥大化 |
| B. ページング（offset/limit 等） | 大量履歴でも応答が安定 | ページング契約の仕様化が必要 |

**推奨案**: 内部デモ目的（simulation-charter §3）からA（全件返却）を推奨。ただし、将来の拡張を見込む場合はB（offset/limitのシンプルな形式）も選択肢。

### DEC-016: 金額の通貨

| 選択肢 | 利点 | 欠点 |
| :--- | :--- | :--- |
| A. 円のみ（単一通貨） | 原始要件の記述（円表記）と一致。実装が単純 | 多通貨対応が将来困難 |
| B. 通貨コード付き | 将来の拡張余地 | 過剰設計の可能性 |

**推奨案**: A（円のみ）を推奨。内部デモ目的では単一通貨で十分。

### DEC-017: メールアドレスの正規化

| 選択肢 | 利点 | 欠点 |
| :--- | :--- | :--- |
| A. 正規化しない（文字列一致） | 実装が単純 | 大文字/小文字の違いで重複が検出できない |
| B. 小文字化・前後空白除去で正規化 | 一意性検証（REQ-CUS-002/004）の信頼性が高い | 正規化ルールの仕様化が必要 |

**推奨案**: B（小文字化・前後空白除去）を推奨。メール一意性の検証精度に直結する。

### DEC-018: 解約（論理削除）の取消・再有効化の可否

| 選択肢 | 利点 | 欠点 |
| :--- | :--- | :--- |
| A. 取消不可（解約は永続） | 状態遷移が単純。監査が容易 | 誤解約の救済ができない |
| B. 再有効化を許可 | 誤操作の救済が可能 | 解約後の操作禁止（DEC-001〜004）との整合設計が必要 |

**推奨案**: A（取消不可）を推奨。解約後の操作禁止と整合し、状態遷移が単純になる。誤解約は新規登録で対応する運用を推奨。

### DEC-019: 同一時刻履歴の決定的順序が必要か（仕様論点）

| 選択肢 | 利点 | 欠点 |
| :--- | :--- | :--- |
| A. 必要ない（時刻のみで並べる） | 仕様が単純 | 同一時刻の履歴の並びが実行環境依存になり再現性がない |
| B. 必要（タイブレーカーを定義） | 履歴の並びが決定的で再現可能 | タイブレーカー（例: 取引ID）の定義が必要 |

**推奨案**: B（必要）を推奨。テスト・監査・追跡可能性（charter §4）の観点で、同一時刻の並びは決定的であるべき。実現技術方式はADR候補（ADR-CANDIDATE-008）。

### DEC-020: 口座番号の外部形式（仕様論点）

| 選択肢 | 利点 | 欠点 |
| :--- | :--- | :--- |
| A. 内部IDと同形式（連番等） | 実装が単純 | 桁数・構成の業務上の意味が薄い |
| B. 業務形式（固定桁・チェックディジット付き等） | 誤入力の検出が可能 | 採番方式の仕様化（ADR-CANDIDATE-009）が必要 |

**推奨案**: 内部デモではA（連番等の単純形式）で開始し、業務形式（B）が必要な場合のみ採用を検討する。外部形式そのものは仕様論点、採番方式はADR候補として分離。

### DEC-021: タイムゾーンの業務上の意味（仕様論点）

| 選択肢 | 利点 | 欠点 |
| :--- | :--- | :--- |
| A. 単一タイムゾーン（JST）前提 | 原始要件の例示（2026-08-01 10:00:00）と整合。実装が単純 | 多タイムゾーン対応が将来困難 |
| B. タイムゾーンを業務要件として定義 | 将来の拡張余地 | 過剰設計の可能性 |

**推奨案**: 内部デモではA（JST前提）を推奨。DB保存方式（UTC保存等）はADR候補（ADR-CANDIDATE-010）として分離。

### DEC-022: 内部デモ運用要件の水準（health check・ログ・バックアップ・復旧）

| 選択肢 | 利点 | 欠点 |
| :--- | :--- | :--- |
| A. 最小限（health checkのみ） | 実装が最小 | 障害時の調査・復旧手段がない |
| B. 標準（health check＋ログ＋バックアップ手順） | 内部デモリリース（charter §3）に十分な水準 | 運用成果物（手順書等）の作成が必要 |
| C. 本格（＋復旧訓練・監視） | 堅牢 | 内部デモには過剰 |

**推奨案**: B（health check＋ログ＋バックアップ手順）を推奨。Release Ready（charter §6）の要件（migration・デプロイ・ロールバック検証）と整合させる。

### DEC-023: Accountの状態属性の有無と状態遷移モデル（Customerとの状態同期含む）

| 選択肢 | 利点 | 欠点 |
| :--- | :--- | :--- |
| A. Accountに状態属性を持たせ、Customerと同期（両方とも有効/解約済） | 解約処理（§2.1）の記述と整合。口座単位の状態判定が可能 | 顧客と口座の状態同期の整合性管理が必要 |
| B. 口座は状態を持たず、Customerの状態で判定 | モデルが単純（1顧客＝1口座のため顧客状態で口座状態を導出可能） | 原始要件「口座のステータスを解約済みに変更」の記述と不整合 |
| C. 口座は状態を持たず、顧客状態と別に口座の凍結フラグ等を持つ | 解約以外の口座状態（凍結等）を将来表現可能 | 状態体系が複雑化 |

**推奨案**: 原始要件の記述（「顧客**および口座のステータス**を解約済みに変更」）に忠実なのはA。ただし1顧客＝1口座のため、Bでも業務的には成立する。CON-001（状態属性の不整合）の解消方法としてKooが決定。実現方式（ステータスカラム vs deleted_at）はADR候補（ADR-CANDIDATE-006）。

### DEC-024: 顧客登録と口座開設のトランザクション境界（不可分範囲）

| 選択肢 | 利点 | 欠点 |
| :--- | :--- | :--- |
| A. 顧客作成と口座開設を1トランザクション（不可分） | 1顧客＝1口座（REQ-DOM-001）の不変条件を保証 | トランザクション境界の設計（ADR-CANDIDATE-002）が必要 |
| B. 顧客作成と口座開設を分離し、失敗時は個別リカバリ | 処理の分離が可能 | 口座開設失敗時に顧客のみ残る不整合が発生し得る（R-06） |

**推奨案**: A（不可分）を推奨。1顧客＝1口座の不変条件を保証するため、顧客作成と口座開設は同一トランザクションで実施する。実現方式はADR候補（ADR-CANDIDATE-002）。

### DEC-025: 入金・出金の残高更新と履歴作成の不可分範囲（出金履歴の要否含む）

| 選択肢 | 利点 | 欠点 |
| :--- | :--- | :--- |
| A. 残高更新と履歴作成を1トランザクション（不可分） | 残高と履歴の不一致（R-07）を防ぐ | トランザクション境界の設計が必要 |
| B. 別々に実施し、失敗時はリカバリ | 処理の分離が可能 | 残高と履歴が不一致になり得る |
| C. 出金履歴を作成しない | 実装が最小 | 履歴照会の表示対象（§2.4「出金」）と矛盾する |

**推奨案**: A（残高更新と履歴作成を不可分）を推奨。履歴照会の表示対象に「出金」が含まれるため、出金履歴は必須とし（Cは不採用）、残高更新と履歴作成は同一トランザクションで実施する。実現方式はADR候補（ADR-CANDIDATE-002）。

## 16. 仕様書で決めるべき事項

## 17. ADR候補

**方式選択部分に限り**ADR候補とする。仕様不足（何を決めるか）と方式選択（どう実現するか）を分離している。

| :--- | :--- | :--- |
| ADR-CANDIDATE-001 | 金額の保存形式（整数[銭] / 固定小数 / DECIMAL） | R-04（残高≧0）、浮動小数点誤差の回避 |
| ADR-CANDIDATE-002 | トランザクション境界（振込・顧客登録＋口座開設・残高更新＋履歴作成のアトミック性の実現方式） | R-01, R-06, R-07、REQ-TRF-004、GAP-032〜035 |
| ADR-CANDIDATE-003 | 行ロックの実装方式（`SELECT FOR UPDATE` の適用範囲・ロック取得順・トランザクション分離レベル・ロック待ちタイムアウト） | R-08, R-12、REQ-CON-001 |
| ADR-CANDIDATE-004 | 複数口座のロック順序（デッドロック防止） | R-09、GAP-031 |
| ADR-CANDIDATE-005 | 冪等性の実現方式（冪等キー / リクエストID） | R-08、GAP-029 |
| ADR-CANDIDATE-006 | 論理削除方式（ステータスカラム / deleted_at） | CON-001、GAP-001、DEC-023 |
| ADR-CANDIDATE-007 | 取引履歴の不変性の実装方式（追記専用 / 更新削除禁止） | R-13、GAP-009 |

| ADR-CANDIDATE-009 | 口座番号の採番方式（シーケンス / チェックディジット付き等） | GAP-018、DEC-020 |
