## Executive summary

仕様書は、原始要件、B-01〜B-06、D-01〜D-17の大部分を正確に取り込み、状態、不変条件、金額境界、振込の不可分性、Transactionの不変性、履歴順序、REST APIの共通エラー形式を広く定義している。固定Base/Headの比較でも、変更は対象仕様書1件だけであり、レビュー対象の成立前提に問題はなかった。

一方、Specification Readyへ進むには解消が必要なMajor findingが残る。

特に重要なのは、同一冪等キーの結果再利用と競合後の同一キー再試行が両立する条件が定義されていない点である。現状のままでは、競合結果を永続的に再返却して再試行不能にする実装と、競合後に再実行する実装の両方が仕様適合になり得る。これはD-13とD-17の外部契約を一意に実装できない状態である。

また、Koo決定では解約後に許可する操作を「顧客情報参照と取引履歴閲覧のみ」としているが、仕様書は解約済み口座の口座基本情報参照と現在残高直接参照を明示的に拒否していない。一般権限マトリクスでは管理者・窓口担当者に両操作を許可しているため、状態別の優先規則が曖昧である。

Acceptance Criteriaとトレーサビリティにも重大な不足がある。顧客更新成功、通常出金の0円・負数・最小値・残高同額、振込の残高不足・不存在、未認証401、閲覧者の履歴上残高、並行振込、解約と金銭操作の競合、Audit Logの記録内容等を実質的に検証できない。REQ IDが表に存在するだけで、要件の全意味をAcceptance Criteriaが担保していない行が複数ある。

さらに、管理者の利用者管理・役割管理をv0.1.0の実機能として含める範囲、取引0件時の履歴レスポンス、冪等性キーのライフサイクルについて、新たな製品判断が必要である。

#### M-1 冪等性の結果固定と競合後再試行の契約が一意に成立していない

- 根拠:
  - Issue #8 Koo決定 D-13は、同一冪等キー・同一要求の再送で残高・履歴を重複更新せず、最初と同じ業務結果を返すとしている。
  - Issue #8 Koo決定 D-17は、競合時に固定エラーを返し、利用側が同じ冪等キーで安全に再実行できるとしている。
  - 対象仕様書 §10.4、§11.4、§12.4、AC-IDEM-001は「最初の業務結果」を再返却すると定義する。
  - 対象仕様書 §16.4は、`concurrent_operation_conflict`等の後に同じ冪等キーで再実行できると定義する。
- 問題:
  - `concurrent_operation_conflict`を「最初の業務結果」として固定するのか、再実行可能な一時的結果として扱うのかが未定義である。
  - 冪等キーを確定済みにする結果と、キーを消費せず再試行可能にする結果の区分がない。
  - 同一キー・同一要求が同時到着した場合に、待機して最初の結果を返すのか、retryable errorを返すのかが未定義である。
  - キーのnamespace、要求同一性の判定範囲、保証期間・有効期限が未定義である。
  - 保存テーブル等の実現方式はADR対象だが、利用側から観測される再送結果、キーの適用範囲、保証期間は製品仕様で固定する必要がある。
- 影響:
  - 競合後の再試行が永久に同じ競合結果を返す実装と、再度業務処理を実行する実装の両方が成立する。
  - 同一キーの並行要求で二重実行、永久競合、endpoint間の意図しない衝突が起こり得る。
  - D-13とD-17を満たす自動テストを一意に設計できない。
- 修正方針:
  - Koo承認事項として、少なくとも次を固定する。
    1. 冪等キーのnamespace
    2. 同一要求と判定する項目
    3. 成功、確定的業務エラー、一時的競合、認証・入力エラーのうち、どの結果でキーを確定するか
    4. 同一キーの処理中要求に返す結果
    5. 保証期間またはv0.1.0での無期限保持
  - `concurrent_operation_conflict`を再試行可能とする場合は、その結果でキーを確定しないことを明記する。
  - 同一キー同時送信、競合後再送、異内容再送を分離したAcceptance Criteriaを追加する。
  - 保存方式、排他方式、内部待機方式だけをADRへ分離する。

#### M-5 並行振込・解約競合・同一キー同時送信をAcceptance Criteriaで検証できない

- 根拠:

  - AC-DEP-003は並行入金を対象とする。
  - AC-TRF-002は一般的な振込工程失敗であり、同時振込または出金との競合を検証しない。

- 問題:
  - 原始要件が明示する並行振込を受入条件で検証できない。
  - 同一出金元からの複数振込、逆方向振込、出金と振込の競合、解約と入出金・振込の競合で、どの結果を許可するかがACにない。

- 影響:
  - 負残高、片側振込、誤った取引後残高、解約済み口座の残高変動、重複処理を検出できない。

    - 逆方向の同時振込
    - 解約と入金・出金・振込の競合

  - 成功件数、最終残高、双方履歴、共通振込ID、取引後残高、失敗側code、部分更新なしを検証可能にする。

#### M-6 固定エラーコード案に同一原因の重複と未定義の状態遷移がある

- 根拠:

  - §16.3は、解約済みAccountの禁止操作に`account_closed`、解約済みCustomerの禁止更新に`customer_closed`を割り当てる。
  - AC-CLS-004の再有効化禁止には固定codeがない。
  - 既に解約済みの対象を再度解約する場合の固定codeがない。
  - AC-CLS-003は負残高と状態不整合を一つにまとめるが、§16.3には`data_integrity_violation`と`customer_account_state_inconsistent`の二つの候補がある。
  - AC-TRF-004は自分自身と解約済みを一つにまとめるが、§16.3では別codeである。
- 問題:
  - 同じ解約済みCustomer／Accountペアに対し、endpointにより`account_closed`と`customer_closed`が返り得る。
  - 無効な状態遷移、既解約、状態不整合、負残高の原因分類が一意でない。
  - 原因別codeを機械判定の正本とするB-05の目的を満たせない。

  - API利用側が同じ業務状態へ安定した分岐処理を実装できない。
  - Kooが§16.3を承認しても、実装間で異なるcodeが返る余地が残る。
- 修正方針:
  - 解約済み状態を一つの共通codeへ統合するか、`account_closed`と`customer_closed`を使い分ける厳密な原因規則を定義する。
  - `invalid_state_transition`等、再有効化・既解約に対応する固定codeを追加する。
  - 状態不整合とその他データ整合性異常の境界を明文化する。
  - 複数原因をまとめたACを分割し、各原因のHTTP状態、code、非更新結果を一意にする。
  - 複数不正が同時に存在する場合の評価優先順位を、少なくとも認証、認可、入力、存在、状態、残高、競合の単位で固定するか、優先順位をAPI契約上保証しないことを明記する。
