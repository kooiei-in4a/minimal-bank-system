#### M-3 冪等キーの外部契約にscope・有効期間・失敗時再送の定義がない

- 根拠:
  - Issue #8のD-13は、入金、通常出金、全額出金、振込を冪等対象とし、同じキー・同じ要求では最初と同じ業務結果を返し、異なる要求では拒否することを決定している。
  - 仕様書§10.4、§11.4、§12.4、§18.7は同じキー・同じ要求／異なる要求を記載するが、次を定義していない。
    - キーのscopeがシステム全体、操作種別ごと、操作者ごと、対象口座ごとのいずれか。
    - `同じ要求内容`を構成する項目と、顧客ID／口座番号の表現差を同一要求とみなすか。
    - キーの有効期間または失効条件。
    - 最初の処理が業務エラー、内部エラー、処理中の場合の再送結果。
  - AC-IDEM-001は「金銭操作が成功済み」の再送だけを対象とし、失敗済み・処理中を扱わない。
- 問題:
  - 例えば「同じキーを入金と振込で再利用可能」とする実装と「全操作で衝突」とする実装の両方が仕様適合を主張できる。
  - 失敗後の再送を再評価する実装と、最初の失敗を固定再生する実装が分かれる。
  - 有効期間が無期限か期限付きか不明で、利用側が安全な再送期間を判断できない。
- 影響:
  - 二重処理防止の中心契約がクライアントとサーバー間で一致せず、誤った409、重複実行、永続的な再送不能を招く可能性がある。
  - 外部から観測可能な挙動であるため、保存テーブルやハッシュ方式だけをADRで決めても解消しない。
- 修正方針:
  - Koo承認事項として、少なくともscope、有効期間、要求同一性、成功・業務失敗・内部失敗・処理中の再送結果を決定する。
  - 仕様書へ製品契約を固定し、キー保存、canonicalization、request fingerprint、排他方式等の技術方式だけをADRへ分離する。
  - 各状態を検証するAcceptance Criteriaを追加する。

### Minor

#### m-1 解約時の負残高に対するエラー分類が仕様内で一致しない

- 根拠:
  - §16.3の`account_balance_not_zero`は「残高0円でないため解約不可」とされ、文言上は正残高と負残高の双方を含む。
  - AC-CLS-003は負残高を「内部整合性エラー」として扱う。
  - §16.2では業務競合を409、内部整合性異常を500として分離している。
- 問題:
  - 負残高が409 `account_balance_not_zero`なのか、500 `data_integrity_violation`なのか決定できない。
- 影響:
  - API利用側と受入テストで期待HTTP状態・固定codeが分かれる。
- 修正方針:
  - 推奨は、正残高を409 `account_balance_not_zero`、負残高を不変条件違反として500 `data_integrity_violation`に分離すること。
  - 別方針を採る場合も、§5.3、§16.3、AC-CLS-002／003を同じ分類へ統一する。

#### m-2 振込履歴の送受対応を検証するAcceptance Criteriaが弱い

- 根拠:
  - §12.3は双方のTransactionへ同一振込IDと相手口座番号・相手顧客ID・相手氏名を記録すると定義している。
  - AC-TRF-001は同一振込IDの存在を確認するが、送金側が振込先情報、受取側が出金元情報を保持することを確認しない。
  - AC-HIS-002は各項目が表示されることだけを確認し、値の対応、金額符号、双方の取引後残高の整合を確認しない。
- 問題:
  - 双方へ同じ相手情報を誤記録する、送受を逆転する、金額符号を誤る実装でもACを通過し得る。
- 影響:
  - Transactionの監査価値と振込ペアの追跡性が低下する。
- 修正方針:
  - 具体的な送金元・振込先をGivenへ置き、送金側／受取側それぞれの相手口座番号、相手顧客ID、相手氏名、共通振込ID、金額符号、取引後残高を検証するACへ強化する。
