# 統合・却下・対象外としたFinding

## 1. 目的

Round 1・Round 2で提示された指摘を、モデル名に依存しない根本原因単位へ正規化し、最終Findingへ統合した過程を記録する。

判定区分:

- `ADOPTED`: 独立した最終Findingとして採用
- `MERGED`: 別Findingと同じ根本原因へ統合
- `PARTIAL`: 問題検出は正しいが、重大度、根拠、修正方向の一部を修正
- `REJECTED`: 正本に反する、事実誤認、または問題が成立しない
- `OPTIONAL`: 有用だがSpecification Readyの必須修正ではない
- `API_OR_ADR`: API設計・ADR・実装設計へ委譲可能
- `APPROVAL_REQUIRED`: 正本から問題は確定できるが、完成契約の選択はKoo承認が必要

## 3. Round 2固有候補の審理

| 候補 | 判定 | 理由 |
|---|---|---|
| 振込履歴で相手口座番号を表示することは未承認の情報露出 | REJECTED AS FINAL FINDING | 原始要件のTransaction属性に対当口座番号があり、対象仕様の表示契約を禁止する上位正本はない。表示範囲の改善提案としては検討可能だが、現対象の独立欠陥とは断定しない |
| 振込・解約競合を専用ACで検証 | MERGED → F-002 | §17の契約を受入可能にする論点 |
| 解約・更新の入力識別子が本文で未明示 | OPTIONAL | Issue #7の主要ゲートを止める独立根本原因ではない。API設計時に入力契約を明確化できる |
| 顧客ID採番方式をADR候補へ追加 | OPTIONAL / API_OR_ADR | opaqueな一意識別子として成立し、重要ADRである必然性がない |
| 氏名またはメールだけを部分更新するPATCH意味論 | API_OR_ADR | transport上の省略表現はAPI設計で扱える |
| `no_balance_to_withdraw`が固定code表にない | REJECTED | 対象仕様§16.3に存在する事実誤認 |
| 全額出金の負符号表示を§11.3にも重複記載 | OPTIONAL | §13.4の共通表示契約から一意に導ける |
| 金額は整数円であると物理型まで固定 | PARTIAL / API_OR_ADR | 業務単位が円であることは仕様済み。物理型はADR |
| 顧客IDへ固定外部形式を要求 | REJECTED / OPTIONAL | 正本は一意識別子を要求するが、固定形式を要求しない |
| 取引履歴のページング追加 | REJECTED | D-06が内部デモでは全件返却と決定済み |
| 解約取消・再有効化を追加 | REJECTED | B-02と対象外に反する |
| 自動リトライをAPI保証へ追加 | REJECTED | D-17に反する |

## 5. 承認事項の整理

### 既存§22.1承認事項

1. 固定エラーコード名とHTTP状態の対応
2. 氏名・メールアドレスの最大長・詳細形式を製品契約として固定するか
3. Audit Log閲覧機能をv0.1.0へ含めるか

### 新規Koo承認事項

1. F-003 冪等性外部契約
2. F-004 利用者管理・役割権限管理のv0.1.0契約
3. F-008 Transaction 0件時の履歴レスポンス

F-008はMinorであり、Majorの妥当性を不確定にするものではない。F-003とF-004は、Findingの存在と決定軸までは一意に確定しているため、審理成果物と修正ベンチマークの作成は可能である。修正モデルは完成判断を代行せず、`BLOCKED_BY_APPROVAL`として報告する。
