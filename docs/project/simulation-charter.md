# 開発シミュレーション憲章

- Status: Active
- Repository: `kooiei-in4a/minimal-bank-system`
- Initial phase: Requirements Review

## 1. 目的

最小銀行システムを題材に、要件定義から内部デモリリースまでを実行し、次の開発モデルが一貫して機能するかを検証する。

- 仕様駆動開発
- ADR駆動開発
- AI-PR駆動開発
- 実装者・独立レビュアー・リリースレビュアーの役割分離

## 2. シミュレーション対象

- 顧客登録、更新、解約
- 口座自動開設
- 入金、出金、全額出金
- 口座間振込
- 取引履歴照会
- 残高整合性、排他制御、入力検証

## 3. リリース境界

最終成果物は`v0.1.0`の内部デモとする。

- 実行先はlocalhostまたは閉域検証環境とする。
- 実在する顧客、口座、送金、金融機関には接続しない。
- 法令準拠済みの銀行勘定系システムとして扱わない。
- 公開インターネット上で金融サービスとして提供しない。

## 4. 追跡モデル

`Requirement → Specification → ADR → Issue → Pull Request → Test → Release Evidence`

各要件は、最終的に仕様、実装Issue、PR、検証証拠へ追跡できなければならない。

## 5. フェーズ

1. 要件定義レビュー
2. 仕様化と受入条件の固定
3. ADRの作成と承認
4. 実装Issueの分割
5. AI-PR駆動実装
6. 独立レビューと修正
7. 統合・システムテスト
8. Release Candidate検証
9. 内部デモリリース
10. 事後評価

## 6. フェーズゲート

### Requirements Ready

- 原始要件に要件IDが割り当てられている。
- 矛盾、不足、未決事項が記録されている。
- 実装を妨げる未決事項が決定されている。

### Specification Ready

- 正常系、主要異常系、状態遷移、受入条件、対象外が定義されている。
- 要件と仕様の対応関係が確認できる。

### Architecture Ready

- 重要な設計判断がADRとして承認されている。
- データ整合性、トランザクション、排他制御の方式が固定されている。

### Implementation Ready

- Issueの範囲、対象外、依存関係、検証方法が明確である。

### Merge Ready

- 受入条件を満たす証拠がある。
- 独立レビューのBlockerとMajorが解消されている。
- 必須CIが成功している。

### Release Ready

- migration、デプロイ、smoke test、ロールバック手順が検証済みである。
- 既知制約が明示されている。
- KooがGo判断を行っている。

## 7. 完了条件

- `v0.1.0`の内部デモリリースが作成されている。
- 全要件のトレーサビリティが確立している。
- 開発方式の有効性、欠点、改善案を事後評価として記録している。
