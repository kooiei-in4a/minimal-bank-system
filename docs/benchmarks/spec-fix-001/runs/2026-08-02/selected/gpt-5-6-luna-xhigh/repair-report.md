## Open approval items

### 冪等性の外部契約

次の8軸をKoo承認後に確定する。各選択は、同一要求として再実行できる範囲、重複防止の判定、利用側が再試行できる結果および保証期間に影響する。

1. key scope / namespace: 操作単位、利用者単位等の範囲の選択が、別操作間のkey衝突と再送認識範囲に影響する。
2. request identity: どの要求項目を同一性に含めるかの選択が、同一要求と異なる要求の判定に影響する。
3. 顧客ID指定と口座番号指定の同一性: 同じAccountへの別指定を同一要求と扱うかの選択が、安全な再送の判定に影響する。
4. 結果確定区分: 成功、拒否、処理中、結果不明等の区分が、再送時に返す業務結果と利用側の対応に影響する。
5. 競合時にkeyを消費するか: 消費するか再利用できるかの選択が、競合後に同じkeyで安全に再実行できる範囲に影響する。
6. 処理中の再送結果: 待機、競合、処理結果再利用等の選択が、同時到着時の外部応答に影響する。
7. 同一key・異なるpayloadの結果: 拒否その他の結果区分の選択が、keyの取り違えと意図しない金銭操作の防止に影響する。
8. 保証期間・expiry: 保持期間や期限切れの選択が、遅延した再送を同一結果として保証する範囲に影響する。

承認後は、同一要求の再送、同一要求の同時到着、処理中の再送、異なるpayload、競合後の再実行および保証期間を原因別に受入条件へ追加する。

### 利用者管理・役割権限管理

次をKoo承認後に確定する。選択結果は、利用者が利用できる外部操作、権限境界、利用者状態、最後の管理者を維持できるか、監査証跡および拒否時の利用者体験に影響する。

1. 製品APIか初期構築・運用手順か: 製品利用者に見える機能として提供するか、内部手順に限定するかが、外部契約の有無に影響する。
2. 最低限の利用者管理操作集合: 作成、変更、無効化等の範囲が、管理者の操作権限と受入対象に影響する。
3. 利用者の状態: 状態と遷移の選択が、ログイン可否と既存操作の扱いに影響する。
4. 固定3役割の付与だけか、役割定義の編集も許すか: 付与だけにするか定義編集まで許すかが、権限の固定性と管理対象に影響する。
5. 最後の管理者を失うこと等の禁止条件: 禁止するかの選択が、管理不能状態の防止に影響する。
6. Audit Logの対象範囲: 利用者・役割変更をどこまで記録するかが、操作追跡の完全性に影響する。
7. 管理者の成功結果と非管理者の403受入条件: 成功時の外部結果と非管理者の拒否をどう検証するかが、権限契約の明確性に影響する。

承認後は、管理者の成功操作、非管理者のHTTP 403、利用者状態の境界、禁止条件およびAudit Logを原因別に受入条件へ追加する。

### 取引0件の履歴照会

次をKoo承認後に確定する。選択結果は、クライアントが正常な空結果として扱えるか、再試行・エラー処理を行うか、Account不存在や識別子不一致を誤認しないかに影響する。

1. Accountが存在しTransactionが0件の場合のHTTP状態: 成功系・別の状態等の選択が、クライアントの再試行とエラー分類に影響する。
2. 返却collectionの形状: 空collectionの表現方法の選択が、クライアントのレスポンス解析に影響する。
3. Account不存在との区別: 別結果にする方法の選択が、存在確認と空結果の誤認防止に影響する。
4. 顧客ID・口座番号の識別子不一致との区別: 別結果にする方法の選択が、入力不整合と正常な0件の誤認防止に影響する。

承認後は、既存Account・Transaction 0件、Account不存在、識別子不一致を別々に実行し、承認されたHTTP状態とcollection形状、外部結果の区別を検証する受入条件を追加する。

既存の§16.3の固定コード・HTTP対応、氏名・メールアドレス制約、Audit Log利用者向け閲覧機能の承認事項も維持する。
