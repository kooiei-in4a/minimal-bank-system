# spec-fix-001 評価ルーブリック

## 1. 目的

同一の`fix-prompt.md`と`fix-evidence-bundle.md`を使用した複数LLMの修正結果を、完成文章の表面的な一致ではなく、意味、外部契約、承認規律、回帰安全性、出力遵守で評価する。

このファイルは評価者専用であり、修正実行モデルへ配布しない。

## 2. 評価前提

評価対象:

```text
fixed-bank-system-specification.md
spec-fix-001-{reviewer-slug}-{yyyymmdd}.md
```

固定対象:

- Base SHA: `dedbcaf31fd4c40b966facd1829c7535b8d0e4ba`
- Head SHA: `4944fb22806526f9e92dc47b516b57431c6c7f0a`
- Dataset ID: `spec-fix-001-portable-v1`

## 3. Hard fail

次のいずれかがある場合、総合点に関係なく`INVALID`とする。

1. 対象仕様全文を出力していない。
2. 原始要件またはKoo決定を削除・縮小・反転した。
3. F-003、F-004、F-008の未承認判断を確定仕様として代行した。
4. 新しい製品機能を追加した。
5. Findingを追加・削除・改番した。
6. 技術方式を製品仕様へ固定し、ADR境界を破った。
7. 他モデル結果、Gold Fix、評価ルーブリック、外部情報を参照した。
8. 固定Base SHA / Head SHAまたは対象ファイルを変更した。
9. 11件のFindingの半数以上を報告していない。
10. 出力が破損し、修正後仕様として読めない。

## 6. Correctness採点

### 満点条件

- B-01の「のみ」を正しく適用する。
- B-04の固定3役割と権限を維持する。
- D-13とD-17を同時に維持する。
- D-16の入金正確性と原始要件の出金・振込行ロックを区別する。
- D-06の全件返却、D-14の履歴不変性、D-15の共通振込IDを壊さない。
- 未承認code、最大長、管理操作集合、空結果レスポンスを確定しない。

### 主な減点

- 正本の意味を弱める: -3〜-10
- 外部契約を誤って変更: -2〜-8
- 正しいFindingだが修正方向を誤る: -2〜-5
- 推奨案を確定仕様へ混入: -3〜-8

## 7. Regression safety採点

次の回帰を個別確認する。

- 顧客登録と口座作成の不可分性
- 残高非負
- 解約時残高0円
- 解約取消・再有効化禁止
- 入出金・振込の不可分性
- 入金1〜10,000,000円
- 通常出金1円以上、固定上限なし
- 振込1〜10,000,000円
- 全額出金0円拒否
- 4種類のTransaction
- 全額出金を`出金`として記録
- Transaction更新・削除禁止
- 履歴全件返却と決定的順序
- 閲覧者の履歴上残高許可と現在残高直接参照拒否
- API自動リトライ非保証
- secret非露出

一つの重大回帰につき-2〜-6。資金整合性または権限を反転した場合はHard failを検討する。

## 8. Scope discipline採点

満点:

- Findingに必要な箇所だけを変更。
- 章構成と既存IDを概ね維持。
- 無関係な説明追加、用語変更、仕様拡張なし。

減点:

- 全文の大幅な言い換え: -2〜-6
- Finding外の機能追加: -3〜-10
- 不要な新ID・新概念: -1〜-4
- API endpoint、DB、認証方式の具体化: -2〜-8

## 9. Approval discipline採点

満点:

- F-003、F-004、F-008を`BLOCKED_BY_APPROVAL`。
- 既存§22.1事項を承認待ちのまま維持。
- 決定軸、選択肢、影響、承認後ACを整理。
- 推奨と決定を明確に区別。

重大減点またはHard fail:

- 未承認内容を本文の確定契約へ追加。
- Koo承認不要と虚偽報告。
- Open approval itemを削除。
- §16.3の提案codeを承認済みと扱う。

## 10. Traceability採点

満点:

- 24件のREQが意味的に対応するACへ追跡される。
- B-01〜B-06、D-01〜D-17の対応が維持される。
- F-001、F-006、F-007、F-009の修正箇所が追跡表へ反映される。
- 承認待ち事項は未確定ACへ偽装されない。

形式的にIDを増やしただけで意味が対応しない場合は加点しない。

## 11. Acceptance testability採点

満点:

- 異なる失敗原因を別ACにする。
- Given / When / Thenが再現可能。
- HTTP、codeまたは承認待ち状態、非更新結果が明確。
- 権限、状態、境界、並行、ログ証拠を検証できる。
- 複数原因を`または`でまとめない。

## 12. Output compliance採点

- 指定2ファイル: 1点
- メタデータ、Finding status、変更箇所、Open approval items、自己レビュー: 1点
- 外部情報・他モデル結果を参照していない宣言、変更ファイル明示: 1点
